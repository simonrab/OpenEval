# CI / scheduled recheck

This slice is for the non-interactive job that re-runs frozen evals. It does not cover starting a feature, naming a model, or the mark screen.

## User

**Who:** a CI job or a timer. Not a person. Not a dashboard.

**What it has:** a project id, a saved eval-set version, the named model, customer keys, and a spend cap for this run. It may also have a bad example from a log, a failed run, or a file the pipeline was given.

**Job:** run the same evals again after a code change, a prompt change, a vendor model change, or on a schedule. Fail the build if the named model now fails. Do not change live traffic.

**Cannot:** wait for a person. Open a mark screen. Pick a new model. Write the named model into the app. Send live user requests through this tool.

A later agent or person acts on the codes this job returns.

## Terms used here

Defined once. The rest of this file uses these words.

| Term | Meaning |
| --- | --- |
| Eval | One example plus how to score whether the model did the job. |
| Eval set | A versioned list of evals. Id prefix `ste_`. New work makes a new version. Old versions stay. |
| Frozen eval-set version | The `ste_` this job was told to use. This job does not edit it. |
| Code eval | A program scores it. No person on each run. |
| Draft eval | Suggested. Not trusted yet. |
| Marked eval | A person set the right answer or pass/fail. Two people agree, or a third decides. Then it is trusted. |
| Trusted eval | A code eval, or a marked eval. Only these gate pass/fail for the named model. |
| Named model | The model the agent should put in the app. Id prefix `rec_`, plus a model id like `provider/model`. We recommend it. We do not apply it live. |
| Failure | A bad example. It is a candidate eval until `register_failure` adds it. |
| Run | Scoring one or more models on one eval-set version. Stores quality, time, and cost. Id prefix `run_`. |
| Recheck | Run the frozen evals again with the same scoring. |
| Cost cap | Max dollars this run may spend on model calls. |
| Partial results | The evals that finished before the cap (or a stop). Stored under a run id. |
| Fail the build | The CI job exits unsuccessful so merge or deploy stops. This is not a model change. |
| Live traffic | Real user requests in the app. This tool never sends them and never switches the model that serves them. |

Eval ids use prefix `cas_`. Project ids use `prj_`. Async work uses `job_` (the run job, not the product "job" object).

## What this user calls

| Tool | When |
| --- | --- |
| `run_evals` | Recheck the frozen eval-set version against the named model. |
| `get_eval_report` | Poll the async run. Read pass/fail, time, cost, and codes. |
| `register_failure` | Turn a bad example into a new eval on a **new** eval-set version. |

This user does not call `recommend_models`. If the named model fails, the output says `need_new_model` and `next_action` may name `recommend_models` with `intent: "after_failure"` for a later agent. This job does not run that step.

This user does not mark examples. If a person is needed, the output says so and the build fails.

## J5 — A failure becomes an eval

**Given** a bad example and an existing eval set.

**When** the job (or a hook it runs) calls `register_failure`.

**Then** the tool copies every old eval into a **new** eval-set version and adds the example as a new eval. The frozen version this recheck used is unchanged. Old evals stay in both versions.

### How the example is scored

A program scores the new eval when at least one of these is true:

1. The caller sent a program check (expected field, valid JSON, right tool name, must-not-contain, a fixture file).
2. The job type already has a program check that fits this input, and no person is required to know the right answer.

Then the new eval is a code eval. It is trusted. `next_action` is `run_evals` on the **new** `ste_`. No mark queue.

A person is needed when a program cannot decide (tone, fuzzy “good reply”, no single right JSON). Then the new eval is a draft. It is not trusted. `next_action` is mark (`queue_for_labeling`). This CI job cannot mark. It fails the build with `need_more_evals`. It does not treat the draft as a pass or a fail of the named model.

A model may suggest a check or an expected answer. A program or a person must confirm. A model does not create a trusted eval by itself.

### Keep old evals

- New eval-set version. New `ste_` id. New `version` number.
- Every eval from the previous version is in the new version.
- Do not delete old evals. Do not edit the old `ste_` in place.
- Next `run_evals` on the new version includes the new eval **and** the old ones.

If the same example is registered again with the same `idempotency_key`, return the existing new `ste_` and `cas_`. Do not add a duplicate eval.

### Inputs

```jsonc
{
  "project_id": "prj_...",
  "eval_set_id": "ste_...",          // current (often frozen) version
  "input": {                        // the bad example
    "prompt": "string",
    "files": [{ "path": "string" }]
  },
  "trace": "string",                // optional, short
  "program_check": {                // optional; if present, this is a code eval
    "kind": "json_valid" | "tool_name" | "field_equals" | "must_not_contain" | "fixture",
    "expected": {}
  },
  "idempotency_key": "string"
}
```

### Outputs

```jsonc
{
  "eval_set_id": "ste_...",          // NEW version
  "previous_eval_set_id": "ste_...",
  "version": 4,
  "case_id": "cas_...",
  "score_kind": "code" | "needs_person",
  "trusted": true,
  "old_eval_ids": ["cas_..."],
  "next_action": {
    "tool": "run_evals" | "queue_for_labeling",
    "args": {}
  }
}
```

`trusted` is true only for a code eval. For `needs_person` it is false.

### Done when

- A new `ste_` exists.
- The new eval is on it.
- Every old eval is still on it.
- The previous `ste_` still exists and still matches what this recheck ran.
- If `score_kind` is `code`, a later recheck of the **new** version scores the new eval with a program.
- If `score_kind` is `needs_person`, the new eval is draft, a mark link is the next action, and this CI job has exited unsuccessful.

## J7 — Check again later on a saved eval-set version

**Given** a saved eval-set version and a named model.

**When** CI or a timer calls `run_evals` with `intent: "recheck"`.

**Then** the tool runs the **same** evals with the **same** scoring. It reports pass/fail, time, and cost for the named model. It does not add evals. It does not drop evals. It does not write a new named model. It does not change live traffic.

### Fail the build. Do not change live traffic.

If the named model fails any trusted eval, or misses the job's time or spend limits, this job fails the build.

Return `need_new_model` when the named model now fails. A later agent may call `recommend_models` with `after_failure`. This job does not.

Return `does_not_work` only if this run also scored the backups on the same `rec_` and those fail too. CI still does not name a model. CI still does not change live traffic. A recheck that scored only the named model uses `need_new_model`, not `does_not_work`.

A green result on the frozen evals is not a pass if the job was also given new bad examples that are not in this eval set. Return `evals_missing_new_failures`. Next action is `register_failure` (J5). Then fail the build.

Recheck never swaps the production model. The app keeps using whatever model is already in its config until a person or an agent changes that config.

### What this run scores

- Trusted evals on the frozen `ste_` only.
- Draft evals waiting for a person are not scored as pass/fail.
- If trusted evals are too few to trust a pass, return `need_more_evals` and fail the build. Do not report a pass.

Same scoring means: the same program checks, and the same marked answers. Do not invent new expected answers on a recheck.

### Inputs

```jsonc
{
  "project_id": "prj_...",
  "eval_set_id": "ste_...",            // frozen version; required
  "named_model": {
    "rec_id": "rec_...",               // required
    "model_id": "provider/model"       // required; must match rec_
  },
  "intent": "recheck",
  "max_eval_spend_usd": 2.0,           // cost cap for this run
  "new_failures": [                    // optional; examples not yet in the set
    { "input": { "prompt": "string" }, "trace": "string" }
  ]
}
```

`run_evals` is async. Immediate output is `{ "job_id": "job_...", "status": "queued" }`. CI polls `get_eval_report` with `job_id`. It must not exit 0 while status is `queued` or `running`.

Customer keys on the project are used for model calls. This job does not prompt for keys.

### Outputs (when the run finishes)

```jsonc
{
  "status": "passed" | "failed" | "cost_cap",
  "code": null | "need_new_model" | "does_not_work" | "evals_missing_new_failures" | "need_more_evals" | "COST_CAP_EXCEEDED",
  "eval_set_id": "ste_...",
  "named_model": { "rec_id": "rec_...", "model_id": "provider/model" },
  "run_id": "run_...",
  "quality": 0.86,
  "p50_ms": 820,
  "cost_usd": 0.41,
  "limits_ok": true,
  "failing_eval_ids": ["cas_..."],
  "new_failure_ids_missing": [],
  "live_traffic_changed": false,
  "ci_exit": 0,
  "next_action": { "tool": "string", "args": {} },
  "report_url": "https://..."
}
```

`live_traffic_changed` is always `false` for this user.

`ci_exit` is `0` only on a complete pass (see Build exit). Otherwise it is non-zero.

`code` is `null` only on that complete pass.

### Done when

- The run used the given `ste_` and did not mutate it.
- Scoring matches the saved evals.
- The report includes pass/fail, time, and cost for the named model.
- If the named model now fails: `need_new_model` or `does_not_work`, `ci_exit` non-zero, live traffic unchanged.
- If new bad examples were given and are not in the set: `evals_missing_new_failures`, `ci_exit` non-zero. That is not a pass.

## Cost cap and partial results

**Given** a recheck (or a run after J5) with `max_eval_spend_usd`.

**When** spend on this run reaches that cap before every trusted eval is scored.

**Then** stop further model calls. Store what finished. Return `COST_CAP_EXCEEDED` and the partial results id (`run_id`). Fail the build. Do not change live traffic. Do not treat a partial pass as a pass.

### Rules

- Default cap comes from the project or from the call. The call value wins if both exist.
- Count only this run’s model-call spend toward the cap.
- Stop between evals, not in the middle of writing a stored row for an eval that already returned.
- Partial results list which `cas_` ids ran, which did not, quality/time/cost for those that ran, and spend so far.
- `get_eval_report` with that `run_id` returns the partial set. Status is `cost_cap`.
- A later job may re-run with a higher cap, or continue from the same frozen `ste_`. It must not skip failed evals from the partial set.

### Inputs (on `run_evals`)

`max_eval_spend_usd` (number, required for CI). Reject the call if missing or `<= 0`.

### Outputs (when the cap hits)

```jsonc
{
  "status": "cost_cap",
  "code": "COST_CAP_EXCEEDED",
  "run_id": "run_...",
  "partial": true,
  "spend_usd": 2.0,
  "cap_usd": 2.0,
  "eval_ids_scored": ["cas_..."],
  "eval_ids_not_scored": ["cas_..."],
  "live_traffic_changed": false,
  "ci_exit": 1,
  "next_action": { "tool": "run_evals", "args": { "eval_set_id": "ste_...", "max_eval_spend_usd": 4.0 } }
}
```

### Done when

- Spend did not go past the cap by more than the last in-flight call.
- A `run_id` exists and is readable.
- Unscored trusted evals are listed.
- The build failed.
- Live traffic is unchanged.

## Error codes

Every error has `code`, `retryable`, `suggested_tool`, `suggested_args`, and `next_action`.

| code | meaning | CI build | next |
| --- | --- | --- | --- |
| `need_new_model` | Named model failed trusted evals or job limits | fail | Later: `recommend_models` with `after_failure`. Do not swap from CI. |
| `does_not_work` | No allowed model passed these trusted evals | fail | Show `failing_eval_ids`. Do not name a model. |
| `evals_missing_new_failures` | New bad examples are not in this eval set | fail | `register_failure` |
| `need_more_evals` | Not enough trusted evals, or a new failure needs a person | fail | Mark or add code evals. CI does not mark. |
| `COST_CAP_EXCEEDED` | This run hit the spend cap | fail | Read partial `run_id`. Re-run with a higher cap if you must finish. |
| `SUITE_NOT_FOUND` | Bad or unknown `eval_set_id` | fail | Pass a saved `ste_` |
| `PROJECT_NOT_FOUND` | Bad `project_id` | fail | Pass a real `prj_` |
| `NAMED_MODEL_MISMATCH` | `rec_id` does not match `model_id`, or no named model on the project | fail | Pass the saved named model |
| `COST_CAP_REQUIRED` | CI recheck omitted `max_eval_spend_usd` | fail | Set the cap and retry |

`JOB_UNCLEAR` is not this user’s job. Recheck does not write new evals from a job description.

## Build exit

| Result | `ci_exit` |
| --- | --- |
| Named model passed all trusted evals on the frozen version, inside time and spend limits, run complete, no new failures missing from the set | `0` |
| Any code in the table above | non-zero |
| Run still `queued` or `running` when CI’s own clock runs out | non-zero |

Exit `0` is the only pass. A skip, a timeout, a partial run, or a draft-only set is not a pass.

Failing the build does not change the named model and does not change live traffic.

## Done when (this user)

- Recheck runs on a saved `ste_` with the named model and the same scoring.
- The build fails if the named model now fails, if new failures are missing from the evals, if trusted evals are too few, or if the cost cap stops the run.
- J5 adds a failure on a new eval-set version and keeps old evals.
- A program-scored failure becomes a trusted code eval with no mark step.
- A failure a program cannot score stays draft and fails this build with `need_more_evals`.
- Live traffic is never changed by this job.
- Partial results after a cost cap are stored and readable.

## Out of scope for this user

- Naming a new model (`recommend_models`).
- Writing that name into the app or into production config.
- Marking examples.
- Rewriting the prompt.
- Sending live user requests through this tool.
- Editing or deleting a frozen eval-set version.
- A dashboard. A report URL in the output is enough.
